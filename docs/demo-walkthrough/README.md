# G-SYS Online Ordering Prototype ウォークスルー

このウォークスルーは、9/17デモ台本（`docs/9-17-demo-script.md`）ではなく、システムの全体像を理解するための資料である。

**改訂履歴**: 本書は初版（承認Workflow・Revision・Supplier Contact/Mail Template・G-SYS正式PO連携・Fulfillment・Follow-up・Legacy PO Concurrency Foundationのいずれも実装前）をPhase 7-Eで全面改訂した。旧版が参照していた「発注内容を確定」ボタン・「発注準備完了」Statusは、Phase 7-C1のV8 migrationで廃止済みであり、現行画面には存在しない。スクリーンショット（01〜06）は現行UIで撮り直し済み。**Phase 8-J追記**: 価格変更（Phase 8-A/8-B）・入荷確認／倉庫在庫（Phase 8-G）・在庫・販売確認（Phase 8-H）の4画面が11章として追加された。これらは元々Order Coreフロー（1〜10章）より後に実装されたため未掲載だったもので、Phase 8-J時点でDashboardからの導線（Navigation Card・KPI）も新設された。11章の4画面には**スクリーンショットは未取得**（後述）。

## 業務フロー

```
発注候補
  ↓
Draft
  ↓
PO Preview
  ↓
承認（OPERATOR申請 → ADMIN承認）
  ↓
Demo Send
  ↓
メーカー回答
  ↓
確認事項 / Revision・Agreement
  ↓
履歴
```

**G-SYSにある在庫・販売・発注残等をもとにRecommended Qtyを提示し、人が発注数量を判断し、管理者の承認を経て、メーカー回答・差異管理まで一連で管理するPortal。**

## 1. Dashboard

![Dashboard](01-dashboard.jpg)

### この画面は何か

ログイン後、最初に表示される画面。今、対応すべきことが何件あるかを一目で把握する入口。Sales Trendや粗利といったAnalyticsの画面ではなく、あくまで今日の作業起点（Action / Operation Cockpit）である。

### ここで見るもの

- 発注候補：Recommended Qty > 0のSKU件数
- 欠品／長期欠品：現在の暫定ロジックにより欠品／長期欠品と判定されているSKU件数（正式な判定条件はGulliver社の現行業務運用を確認したうえで最終確定する。詳細は`docs/9-17-demo-script.md`21章参照）
- 発注作成中：Draft作成済みでまだ承認依頼していない件数
- 承認待ち：ADMINの承認待ちの件数
- メーカー回答待ち：メーカーへ送信済みで回答待ちの件数
- 要確認：Acknowledge待ちの確認事項件数
- 問い合わせ中：Close待ちの問い合わせ件数
- **価格変更（下書き）**（Phase 8-J追加）：価格変更DRAFT件数
- ブランド別内訳：上記をBrand単位で分解した表
- **入荷確認／倉庫在庫／在庫・販売確認への遷移カード**（Phase 8-J追加）：件数は付けず、各画面への入口のみを提供する素のNavigation Card（11章参照）

### 次に何をするか

「発注候補」タイルまたはブランド行をクリックし、Order Candidate Listへ進む。

## 2. Order Candidate List（発注候補一覧）

![Order Candidate List](02-order-candidates.jpg)

### この画面は何か

Legacy G-SYSの在庫・販売実績・発注残の情報と、既存の発注判断Formulaを使って、「何をどれだけ発注すべきか」を一覧で見る画面。

### ここで見るもの

- 商品名・Brand・Supplier
- 現在庫・安全在庫・発注残
- 当月販売数・Lead Time
- 推奨発注数（Recommended Qty）：0件のSKUと算出されているSKUが混在していることが分かる
- 商品状態（通常／廃番／発注停止等）と在庫判定（暫定）（通常／欠品／長期欠品）：Legacy Item Masterに基づく商品状態と、現在庫・発注残から暫定算出した在庫判定は別列・別バッジの独立した情報であり、商品状態＝通常のSKUが在庫判定＝長期欠品になるケースもある（矛盾ではない）。ダッシュボードの「欠品」「長期欠品」タイル・ブランド行から遷移した際は、該当SKUの行にこのバッジが表示される。在庫判定の正式な判定条件は`docs/9-17-demo-script.md`21章のとおりCustomer Review対象。

### 次に何をするか

発注したいSKUをチェックボックスで選択し、「選択した◯件でドラフト作成」でOrder Draftへ進む（複数メーカーの混在選択は不可）。

## 3. Order Draft（発注ドラフト）

![Order Draft](03-order-draft.jpg)

### この画面は何か

システムが数量を決定するのではなく、Recommended Qtyを参考にしながら、人が最終的な発注数量を判断・入力する画面。

### ここで見るもの

- 推奨発注数（Recommended Qty）と発注数（Order Qty）の並び
- 推奨値から大きく外れた場合に表示される「要確認」警告
- SKUごとの単価・金額、合計数量・合計金額
- 「ドラフトを保存」で何度でも編集・再保存できること

### 次に何をするか

内容を確定させたら「PO プレビュー」でPO Previewへ進む。あるいは「承認依頼」で直接、次章の承認Workflowへ進むこともできる。

## 4. PO Preview（PO プレビュー）

![PO Preview](04-po-preview.jpg)

### この画面は何か

メーカーへ発注する直前の最終確認画面。Draftの内容を確認用に表示するだけで、ここから数量を直接編集することはできない。

### ここで見るもの

- SKUごとの発注数量・単価・金額
- 発注数量合計・発注金額合計
- メーカーへの送付内容（宛先・件名・本文）のプレビュー（デモ用の固定値。実際のメーカー担当者Master・メールテンプレートを使った「メールプレビュー」機能とは別物）
- 「デモモードのため、実際のメールは送信されません」という注記

### 次に何をするか

「発注内容を修正」でOrder Draftへ戻るか、Order Draft側から「承認依頼」を行い、次の承認Workflowへ進む。**承認が完了する（Status=承認済み）まで、このPreview画面に「メーカーへ送信」ボタンは表示されない。**

## 5. 承認Workflow（OPERATOR申請 → ADMIN承認 / 修正承認 / 差し戻し）

### この画面は何か

Draftの内容を、起票した本人（OPERATOR）とは別の管理者（ADMIN）が確認・承認する画面。既存G-SYSには存在しない、Portal導入で新たに実現する2段階の業務分担である。

### ここで見るもの

- OPERATORが「承認依頼」を実行すると、Statusが「承認待ち」になり、以後は本人も含めて発注数量などの編集ができなくなること
- ADMINが発注詳細画面から「承認」「修正」（その場で内容を直して承認）「差し戻し」（理由入力必須）のいずれかを選べること
- 承認するとPrototype PO No.（`PO-DEMO-YYYYMMDD-####`）が採番され、Statusが「承認済み」になること
- 差し戻された場合、OPERATOR側の画面に差し戻し理由がそのまま表示され、修正して再度承認依頼できること

### 次に何をするか

承認済みになったOrderをPO Previewで開き、「メーカーへ送信」（Demo Send）を実行する。

---

## 6. Supplier Response（メーカー回答）

![Supplier Response](05-supplier-response.jpg)

### この画面は何か

発注して終わりではなく、メーカーから実際に何個・いつ納品できるかという回答を記録し、発注内容との差異を管理する画面。回答の入力・保存・確定は、Draft作成・承認依頼と同じくOPERATORが行う（「メーカーから届いた事実をシステムへ記録する」作業であり、差異を業務としてどう扱うかの判断とは別）。

### ここで見るもの

- SKUごとの発注数量と回答数量の並び
- 回答数量が発注数量と一致するSKU（差異なし）と、異なるSKU（「数量変更あり」の確認事項が表示される）
- 回答日・回答メモ
- 「回答を保存」は何度でも可能。全SKUの回答が**保存済み**の状態でのみ「メーカー回答を確定」できること（未保存のまま確定はできない）

### 次に何をするか

「メーカー回答を確定」後、差異がある場合はADMINが「合意する」（差異のまま合意）か「修正版を作成」（Revisionとして再度Draftへ）のいずれかを選ぶ。差異がなければそのまま履歴（History）へ進む。

---

## 7. 確認事項（Attention）とRevision / Agreement

### この画面は何か

メーカー回答に含まれる数量・納期の差異を「確認事項」として可視化し、確認済みにする（Acknowledge）操作と、差異を含んだまま合意する（Agreement）か、修正版（Revision）を作り直すかを選ぶ画面。OPERATORが記録した回答の差異を業務としてどう扱うかを判断するのはADMINの役割であり、Agreement・Revision作成はいずれもADMIN限定の操作である。

### ここで見るもの

- 数量変更・納期変更の確認事項は、ユーザーが明示的に「確認済みにする」操作をするまでACTIVEのまま残ること（一部回答の確認事項は自動解消される点と対照的）
- ADMINが「合意する」を実行すると、差異があるままの内容で合意（Status=合意済み）できること。「合意を取り消す」で理由付きに取り消せること
- 「修正版を作成」を実行すると、発注がDraftへ戻り、Draft編集から承認・送信・メーカー回答までの一連の流れをもう一度たどれること
- 発注詳細画面の「発注内容の履歴（Revision）」「回答履歴（Revision別）」で、過去のRevision・回答が消えずに保持されていること

### 次に何をするか

履歴（History）画面で、Revisionをまたいだ操作履歴（Audit Timeline）を確認する。

## 8. マスタメンテナンス（メーカー担当者 / メールテンプレート）

### この画面は何か

ADMIN限定の画面群。既存G-SYSにはメーカー担当者・メールアドレスやメール文面のMasterが存在しないため、Portal専用のMasterとして新設したもの。画面右上の「マスタメンテナンス」からアクセスする。

### ここで見るもの

- メーカー担当者管理：メーカーコード・ブランドコード（任意）・担当者名・メールアドレス・種別（To/CC）・言語等を登録できること
- メールテンプレート管理：テンプレート種別・宛先条件（メーカー/ブランド別）・言語別に文面を登録できること
- いずれもLegacy側のMasterへは一切書き戻さず、Portal内で完結すること

### 次に何をするか

発注詳細画面の「メールプレビュー」で、登録した内容が実際にどう解決されるかを確認する。

## 9. G-SYS連携・入荷状況・問い合わせ（拡張機能）

### この画面は何か

承認済み以降のOrderの発注詳細画面に段階的に現れる、G-SYSとの連携・突き合わせに関する機能群。

### ここで見るもの

- **メールプレビュー**: 実際のメーカー担当者Master・メールテンプレートを解決して宛先・件名・本文を組み立てる（実送信なし）。正式PO番号が未確定のため件名・本文は現時点では表示されない。
- **G-SYS正式PO連携（Preflight）**: メーカー・ブランド・商品コードがG-SYS Masterと整合しているかを確認（PASS/WARNING/BLOCKED）。実際のG-SYSへのファイル投入・登録は行わない。
- **G-SYS入荷状況（Fulfillment）**: 正式PO番号が連携されたOrderについて、発注・Invoice・入荷・残数量を表示する。
- **問い合わせ（Follow-up）**: 未納・一部納品のSKUについて問い合わせ対象を作成し、メール文面プレビュー・Close・再発注Draft作成ができる。
- **G-SYSとの整合確認（Legacy PO Concurrency）**: G-SYS側の現在状態を基準として記録し、後から変更があれば差分を表示する。

### 次に何をするか

これらはいずれも今回のDemo環境限定の準備（正式PO番号の仮リンク等）を要する場合がある。詳細は`docs/9-17-demo-script.md`を参照。

## 10. Order History / Timeline（発注履歴）

![Order History](06-order-history.jpg)

### この画面は何か

「推奨 → 人の判断 → メーカー回答」という数量の変化と、「誰が・いつ・何をしたか」を後から追跡できる画面。

### ここで見るもの

- SKUごとの推奨発注数・発注数量・回答数量の3段階の並び
- 差異があるSKUに表示される確認事項（Attention）
- 画面下部の「操作履歴」：ドラフト作成から承認依頼・承認・Demo Send・メーカー回答確定・合意・修正版作成まで、実行者・実行時刻付きで記録された一連の操作履歴

### 次に何をするか

これでCore Workflow一巡は完了。Dashboardに戻ると、「要確認」件数などがこの発注の状態を反映していることが確認できる。

## 11. 価格変更 / 入荷確認 / 倉庫在庫 / 在庫・販売確認（Phase 8-J追記）

**スクリーンショット未取得**: 01〜06番のスクリーンショットは既存のCore Workflow（1〜10章）用に撮影されたものであり、本章の4画面は撮り直していない。E2E Test（`arrival-warehouse-stock-visibility-foundation.spec.ts`等）による自動化スクリーンショット取得は今回実施せず、テキストのみの説明に留める（Production接続や手作業を要さない範囲でのみ自動化する方針のため、次回改訂時にE2E経由でのスクリーンショット取得を検討する）。

### この画面群は何か

1〜10章のOrder Coreフローとは独立した、Legacy G-SYSデータのREAD ONLY参照画面群。Phase 8-A/8-B（価格変更）・Phase 8-G（入荷確認・倉庫在庫）・Phase 8-H（在庫・販売確認）でそれぞれ追加された。Nav Bar、およびPhase 8-JからはDashboardからも到達できる。

### ここで見るもの

- **価格変更**（ナビゲーション「価格変更」）: 現在の売価・原価・理論利益率を表示し、価格変更案をDRAFTとして作成・シミュレーションできる。**G-SYSへの反映（Apply）機能は未実装**（DRAFT状態のみ到達可能）。
- **入荷確認**（ナビゲーション「入荷確認」）: PO・Invoice・Arrival・入荷実績数量をSKU単位で横断的に検索・一覧できる。SKU Detail画面から「入荷確認を見る」ボタンで、そのSKUに絞り込んだ状態へ直接遷移できる（Phase 8-J追加、SKUは検索条件として使うのみで、遷移先の一覧に業務的な紐付けが追加されるわけではない）。
- **倉庫在庫**（ナビゲーション「倉庫在庫」）: 倉庫別（WH_CD）の在庫数量をSKU単位で確認できる。Detail Drawerから「SKU詳細を見る」「在庫・販売確認を見る」の2つの遷移ボタンがある（Phase 8-J追加）。**入荷確認とは意図的に非連携**（Legacy Source上、入荷実績と倉庫在庫をTransaction単位で結ぶKeyが存在しないため、Warehouse Stock画面から入荷確認へのリンクは存在しない）。
- **在庫・販売確認**（ナビゲーション「在庫・販売確認」）: 現在庫・当月販売数を一覧確認できる。Candidate Listと同じLegacy Queryを再利用。Drawerから「倉庫在庫を見る」「商品詳細（発注履歴等）を見る」への遷移がある。

### 次に何をするか

いずれもREAD ONLYの参照画面であり、ここから発注等の操作は発生しない。

**Navigation Context（Phase 8-M追記）**: SKU Detail・Order Detailから「入荷確認を見る」等で入荷確認・倉庫在庫・在庫・販売確認へ遷移した場合、遷移先の一覧画面には遷移元へ戻るための「戻る」ボタンが表示される（元の画面のFilter/Page状態も維持される）。Nav Barから直接この画面群を開いた場合（Direct Access）は「戻る」ボタンは表示されない（その画面自体がトップレベルのNavigation先であるため）。この判定はURLの`returnTo`パラメータの有無のみで行われ、Browser Historyには依存しない。
