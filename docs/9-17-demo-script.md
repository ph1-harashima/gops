# 9/17 デモ台本

このドキュメントは、Implementation Step 5の指示（20章相当）に基づき作成した、9/17お客様デモ用の台本である。

**前提**: このドキュメントは実装済みの挙動のみを記載しており、`勝手に新しい業務要件を追加しない`（Step 5指示）という制約に従う。顧客へ確認する質問はすべて `docs/customer-review-decision-package.md` に集約済みの項目から採っており、本書で新たに考案した項目は含まない。

**改訂履歴**: 本書は初版（Implementation Step 5当時、承認Workflow・Revision・Supplier Contact/Mail Template・G-SYS正式PO連携・Fulfillment・Follow-up・Legacy PO Concurrency Foundationのいずれも実装前）をPhase 7-Eで全面改訂した。旧版が参照していた「発注内容を確定」ボタン・「発注準備完了」Status・承認Workflowなしの旧フローは、Phase 7-C1のV8 migrationで廃止済みであり、現行画面には存在しない。

**デモ前の準備**:

1. `cd backend && ./demo-reset.sh` を実行し、Prototype PostgreSQLの業務データ（発注・メーカー回答・確認事項・操作履歴等、詳細は同スクリプトのコメント参照）を空の状態にリセットする。`portal_user`（ログインアカウント）・`supplier_contact`・`mail_template`（Portal専用Master）は保持されるため、再作成は不要。Legacy Demo MySQLはこのリセットの対象外であり、常に同じ24 SKUのマスタ・PO実績データを保持している。
2. 16章（G-SYS入荷状況）・19章（G-SYSとの整合確認）を実演する場合のみ、事前準備が追加で必要になる。**正式PO番号（Official PO No.）を実際にPortal操作で採番する機能は本Phaseでは未実装**（後述15章）のため、これらの画面を「連携済み」の状態で見せるには、デモ前にADMINが以下のSQLで特定のOrderへLegacy側の実績PO No.を仮リンクしておく（Portal UIからは行えない、デモ環境限定の準備作業）:
   ```
   docker exec gsys-prototype-postgres psql -U gsys_portal -d gsys_portal -c \
     "UPDATE portal_order SET official_po_no='PO-OUTDOOR-01' WHERE id=<完納デモ用に承認したOrderのid>;"
   docker exec gsys-prototype-postgres psql -U gsys_portal -d gsys_portal -c \
     "UPDATE portal_order SET official_po_no='PO-OUTDOOR-02' WHERE id=<一部納品デモ用に承認したOrderのid>;"
   ```
   `PO-OUTDOOR-01`はSKU `OD-TENT-001`向けの完納（Fulfilled）Fixture、`PO-OUTDOOR-02`はSKU `OD-TENT-002`向けの一部納品（Partial）Fixtureとして、Legacy Demo MySQLに固定で投入済み。16章・19章を実演しない場合はこの準備は不要。
3. ログインアカウント: OPERATOR = `purchase01`、ADMIN = `admin01`、いずれもパスワード`DemoPass123!`（ローカルDemo環境限定、本番Credentialではない）。**デモは複数の画面をまたいで進行するため、開始直前に一度ログインし直しておく**（セッション有効期限による意図しないエラー表示を避けるため）。

## 1. デモ開始時の説明

- 本システムは「G-SYS Online Ordering Prototype」であり、既存G-SYSのデータと発注計算ロジックを活用して構築する、新しいオンライン発注業務PortalのPrototypeであることを説明する。既存G-SYSそのものを改修・変更したものではなく、既存G-SYSのデータを参照しながら動く別Systemであることを補足する（過度に技術的な説明は避ける）。
- 画面上部の「デモ環境」バッジと、その下の警告バナー（Demo Environment - Legacy互換Demo Instanceのデータを表示しています）を指し、以下を明確にする。
  - 表示されているデータはLegacy本番データではなく、Legacy互換の使い捨てDemoインスタンスのデータであること。
  - 発注処理はすべて「Demo Send」というデモモードであり、実際にメーカーへメールが送信されることはないこと。
- 見せる一連の流れ（発注候補 → Draft → Preview → 承認 → メーカーへ送信 → メーカー回答 → 履歴）は、Recommended Qty計算を含め、既存Legacyの計算式（Formula）をそのまま利用していることを説明する。
- OPERATOR（購買担当）とADMIN（管理者）の2つのRoleがあり、デモ中に何度かログインアカウントを切り替えて進行することを事前に説明しておく（例:「起票はOPERATOR、承認はADMINが行う実際の業務分担を再現しています」）。

## 2. Candidate List（発注候補一覧）で見るポイント

`purchase01`（OPERATOR）でログインし、ダッシュボードの「発注候補」KPIタイルまたは「発注候補」ナビゲーションから発注候補一覧へ遷移する。

- 一覧には現在庫・安全在庫・発注残・当月販売数・リードタイム・推奨発注数・商品状態・単価が並んでいることを見せる。
- ブランド／メーカーのFilterで、ブランド別・メーカー別に発注候補を絞り込めることを示す。
- 商品状態Chip（通常／廃番／発注停止）が一覧上で一目でわかることを示す。
- SKUリンクをクリックするとSKU Detail画面へ遷移し、商品情報・在庫情報・発注情報・Legacy PO実績のみの履歴を確認できることを示す。
- **単価について**: 一覧の単価は、そのSKUの直近の発注実績（PO履歴）から取得した値であり、Legacyに存在する正式なMaster価格表からの値ではない（Legacyには単価Master自体が存在しない）。本Demo環境では実運用データではなくDemo用に投入した参考値であることを説明できるようにしておく。

## 3. Recommended Qty（推奨発注数）の説明

- 推奨発注数は既存Legacyの発注判断Formula（4EU方式のDefault Formula、または一部SKUに設定されたItem別Formula）による計算結果であり、Prototype側で独自の計算式を新たに作っていないことを明確に説明する。
- Item別Formulaの例として `OD-TENT-001`（ファミリーテント L グリーン）を示す。同SKUのみLegacy `MS_FORMULA` にItem別の計算式が設定されており、他の全SKUはLegacy Default Formulaで計算されていることを説明する。
- 推奨発注数が0件のSKU（例: `HM-TOWEL-001`、`KT-KNIFE-001`、`OD-CHAIR-001`）と、推奨発注数が算出されているSKU（例: `HM-MUG-001` 推奨5、`OD-TENT-001` 推奨3）を並べて見せ、「在庫が十分にある場合は0になる」という考え方を説明する。
- 発注残（Open PO）がある状態でどう推奨数に影響するかの例として `HM-RUG-002` / `OD-BAG-002`（いずれも発注残25）を示す。
- 当月販売数が多いSKUの例として `KT-PAN-001`（当月60）／`OD-BAG-002`（当月65）を示す。

## 4. Draftで人が判断する意味

- Candidate Listでは発注数量を直接編集しない。チェックボックスでSKUを選び「選択した◯件でドラフト作成」した時点で、Order Qtyの初期値としてRecommended Qtyがそのままコピーされることを示す（複数メーカーが混在した選択はエラーになり、同一メーカーのSKUのみでDraft作成できることも触れる）。
- Order Draft画面で発注数量を実際に人が変更できることを見せる（例: 推奨5 → 発注8のように変更）。
- 発注数量が推奨発注数から大きく乖離した場合（比率0.5未満または1.5超）に「要確認」警告Chipが表示されることを示し、機械的な推奨値をそのまま鵜呑みにせず、人が最終判断する仕組みであることを説明する。
- 「ドラフトを保存」でOrder Draftが保存され、以後同じDraftを何度でも編集・再保存できることを示す。保存していない変更がある間は「承認依頼」「PO プレビュー」の遷移前に警告が出ることも触れる。

## 5. Preview（PO プレビュー）

- Order Draftから「PO プレビュー」で遷移し、SKU別の発注数量・単価・金額、合計SKU数・合計数量・合計金額を確認できることを示す。
- 金額・合計金額は、いずれも単価×数量の自動計算であることを説明する（2章で説明した通り、単価自体はPO実績由来のDemo参考値であるため、金額・合計金額もそれに準じたDemo参考値である）。
- 「メーカー送付内容」セクションで、宛先（To）・CC・件名・本文・添付ファイル名がプレビュー表示されることを示し、「デモモードのため、実際のメールは送信されません」という注記が明示されていることを確認する。**この内容はデモ用の固定値であり、13〜14章で紹介する実際のメーカー担当者Master／メールテンプレートを使った「メールプレビュー」機能とは別物である**ことを説明できるようにしておく。
- Previewは原則READ ONLYであり、ここから直接内容を編集することはできず、編集は「発注内容を修正」でOrder Draftへ戻って行う設計であることを説明する。

## 6. 承認Workflow（OPERATOR申請 → ADMIN承認 / 修正承認 / 差し戻し）

- Order Draft画面へ戻り、「承認依頼」ボタンをクリックすると確認Dialogが表示され、「承認依頼する」を実行するとStatusが「承認待ち」に変わることを示す。依頼後はOPERATORからは発注数量などを編集できなくなることを説明する。
- ここでログインを`admin01`（ADMIN）へ切り替える。承認待ちのOrderの発注詳細画面には「承認」「差し戻し」に加え「修正」ボタンが表示され、ADMINはその場で内容を修正してから承認できること（修正のうえ承認した場合はAudit Timelineに区別して記録される）を示す。
- 「承認」を実行すると確認Dialogが表示され、承認するとPrototype PO No.（`PO-DEMO-YYYYMMDD-####`形式）が採番されてStatusが「承認済み」になることを示す。
- 「差し戻し」を選択した場合は理由の入力が必須であり、差し戻すとOPERATOR側の画面に差し戻し理由が明示的に表示され、修正して再度「承認依頼」できることを示す（本Phaseでは1回のシナリオで留め、差し戻しは口頭説明のみでも可）。
- OPERATORが直接承認APIを呼び出しても権限エラーになる（Backend側で強制されている）ことに触れてもよい。

## 7. Demo Send（メーカーへ送信）

- ADMINでログインしたまま、承認済み（Statusが「承認済み」）のOrderをPO プレビュー画面で開くと、「メーカーへ送信」ボタンが現れることを示す。承認前・承認待ちの状態ではこのボタンは表示されない（ADMINの承認が送信解禁のGateになっていることを説明できるとよい）。
- 「メーカーへ送信」を実行すると確認Dialogを経て、Statusが「メーカー回答待ち」に変わり、発注詳細画面（メーカー回答が入力できる画面への入口）へ自動的に遷移することを示す。
- この操作は1回の確認ダイアログを経て1回のみ実行される設計であり、二重送信は起きないことを説明する（History画面のTimelineで、Demo Send関連のイベントが1回しか記録されないことを見せると分かりやすい）。

## 8. Supplier Response（メーカー回答）

- ここでログインを`purchase01`（OPERATOR）へ戻す。メーカー回答の入力・保存・確定は、承認とは別の「メーカーから届いた事実をシステムへ記録する」作業であり、OPERATORが行う設計であることを説明する（差異を業務としてどう扱うかの判断は18章のADMIN操作で別途行う）。
- メーカー回答画面で、SKUごとに回答数量・回答納期・回答理由メモを入力できることを示す。
- 「回答を保存」は何度でも実行でき、一部SKUのみ回答した状態でも保存できること（11章のPartial Responseと関連）を示す。
- 全SKUの回答数量が**保存済み**の状態でのみ「メーカー回答を確定」が実行可能になることを示す（未保存のまま確定しようとしても実行できない設計であることに触れてもよい）。確定後はStatusが「メーカー確定済み」になり編集不可になることを示す。

## 9. 数量差異（回答数量が発注数量と異なる場合）

- 回答数量が発注数量と異なる値で保存されると、その行に「数量変更あり」の確認事項（Attention）が表示されることを示す（例: 発注12に対し回答9など）。
- 回答数量が発注数量と一致する場合（例: 発注5に対し回答5）は確認事項が表示されないことも合わせて示し、差異がある場合のみ目印が付く仕組みであることを説明する。

## 10. 納期差異（回答納期が希望納期と異なる場合）

- 回答納期を入力すると、希望納期と異なる場合に「納期変更あり」の確認事項が表示されることを示す。
- 希望納期が未設定（—表示）の状態で回答納期を入力した場合も、値が異なる（未設定 → 具体的な日付）ため同様に確認事項が表示されることを示す。

## 11. 0回答（回答数量 = 0）とPartial Response（一部SKUのみ回答）

- 回答数量に0を入力して保存すると、「回答数量0 SKU数」の集計に反映され、未回答（空欄）とは明確に区別されて表示されることを示す。未回答（空欄のまま）の状態では画面上「未回答」というプレースホルダーが表示され、0との違いが視覚的にも分かることを見せる。
- 複数SKUのDraftで、一部SKUのみ回答数量を入力して「回答を保存」すると、「一部回答」という確認事項が表示され、「回答済みSKU数: 1 / 2」のように未回答件数が可視化されることを示す。
- 残りのSKUも回答して再度保存すると、「一部回答」の確認事項が自動的に解消される（ユーザーがAcknowledgeしなくても消える）ことを示し、History画面のTimelineで「確認事項の発生」→「確認事項の解消」という記録が残っていることを確認する。

## 12. 確認事項（Attention）とAcknowledge

- 数量変更・納期変更の確認事項は、一部回答の確認事項とは異なり自動解消されず、ユーザーが明示的に「確認済みにする」操作（確認事項Chipの✓アイコン）をクリックするまでACTIVEのまま残ることを説明する。
- 発注詳細画面またはメーカー回答画面のどちらからでもAcknowledge操作ができることを示す。
- Acknowledge実行後、確認事項Chipが画面上から消え、Historyの Timelineに「確認事項の解消」イベントが記録されること、さらにダッシュボードの「要確認」件数・ブランド別内訳が即座に減少することを示す（ダッシュボードへ戻って確認するとよい）。
- 確認事項の行は物理削除されず、Acknowledge済みでも履歴としては保持され続けることを説明する（画面上は非表示になるが、データとしては消えていない）。
- **トークポイント（説明用、修正なし）**: 数量差異が解消された後の修正版（18章のRevision）を続けて見せる場合、直前のRevisionで発生した確認事項が画面上に残って見えることがある。これは「過去のRevisionで発生した確認事項の記録」であり、正式な区別方法（現在解決済みかどうかの表示分け）は今後の検討事項として、聞かれた場合に説明できるようにしておく。

## 13. Supplier Contact / Mail Template管理（マスタメンテナンス）

- ここでログインを`admin01`（ADMIN）へ戻す。画面右上の「マスタメンテナンス」から「メーカー担当者」を開く。既存G-SYSにはメーカー担当者・メールアドレスを持つMasterが存在しないため、Portal専用のMasterとして新設したことを説明する。
- 「新規作成」からメーカーコード・担当者名・メールアドレス・種別（To/CC）・言語等を登録できることを示す。
- 続けて「メールテンプレート」を開き、同様にPortal専用のMasterであること、テンプレート種別・宛先条件（メーカー/ブランド別）・言語別に文面を登録できることを示す。

## 14. Mail Preview（発注詳細の「メールプレビュー」）

- 承認済み以降のOrderの発注詳細画面にある「メールプレビュー」セクションを開く。5章で見た「メーカー送付内容」（Demo Send用の固定値）とは異なり、こちらは実際に登録したメーカー担当者Master・メールテンプレートを解決して宛先（To/CC）・件名・本文を組み立てる機能であることを説明する。
- 13章で担当者・テンプレートを登録済みであれば、宛先（To/CC）が実際に解決されて表示されることを示す。
- 件名・本文は、正式なPO番号の採番規則がまだお客様と正式合意できていないため、本Phaseでは表示されない（「未確定の項目があるため、件名・本文は表示できません」という案内が出る）ことを説明する。実送信機能も未実装であり、この画面もあくまでプレビューに留まることを明確にする。

## 15. G-SYS正式PO連携（Preflight）

- 承認済みのOrderの発注詳細画面にある「G-SYS正式PO連携」セクションを開く。「G-SYS連携準備」ボタンを押すと、メーカーコード・ブランドコード・商品コードが既存G-SYSのMasterと整合しているかを確認する結果（PASS/WARNING/BLOCKED）が表示されることを示す。
- 正式PO番号は「正式PO番号未設定」と表示されたままであり、これはエラーではなく、採番規則自体がお客様との合意待ちであるための挙動であることを説明する。
- **この操作ではG-SYSへの実際のファイル投入・登録は一切行われない**（確認のみ）ことを明確に説明する。実際のG-SYS登録・投入結果の確認は、採番規則の合意後に着手する今後のPhaseの範囲であることに触れる。

## 16. G-SYS入荷状況（Fulfillment）

- デモ前の準備（本書冒頭）で正式PO番号を仮リンクしておいたOrderの発注詳細画面を開き、「G-SYS入荷状況」セクションでOrdered/Invoiced/Stock-in/Outstandingの数量が表示されることを示す。
- 完納（例: `OD-TENT-001`）と一部納品（例: `OD-TENT-002`）の2パターンを見せられると、入荷の進捗状況が一目でわかることが伝わりやすい。
- 正式PO番号が未連携のOrderでは「G-SYS正式PO未連携です」という明示的な案内が出て、誤って「未納」等と表示されないことにも触れる。

## 17. 問い合わせ（Follow-up）

- 16章の一部納品状態から、該当行の「問い合わせ」ボタンで問い合わせ対象を作成できることを示す（理由の選択・メモ入力）。
- 作成した問い合わせに対して「メールプレビュー」で問い合わせ文面を確認できること（実送信はしない）、ADMINは「完了にする」で問い合わせをCloseできることを示す。
- 「再発注Draftを作成」から、問い合わせ対象のSKUを引き継いだ新しいDraftを作成できることを示す（数量は自動的には決定されず、Legacy推奨数量が初期値になることを説明する）。

## 18. Revision / Agreement（差異のまま合意 or 修正版作成）

- 引き続き`admin01`（ADMIN）のまま進める。8〜9章でOPERATORが記録した「メーカーから届いた事実（回答数量・納期）」に対し、その差異を業務としてどう扱うか（受け入れるか、発注内容自体を直すか）を判断するのはADMINの役割であることを説明する。8〜9章で数量差異が発生したメーカー確定済みのOrderの発注詳細画面（またはメーカー回答画面）を開く。
- 「合意する」を実行すると、差異がある内容のままメーカー回答内容に合意（Status「合意済み」）できることを示す。未確認の確認事項が残っている場合はチェックボックスで明示的に合意する必要があることも触れる。
- 「合意を取り消す」で理由付きで合意を取り消し、メーカー確定済みの状態へ戻せることを示す（取り消し記録も履歴として残る）。
- 差異を反映した修正版を作りたい場合は「修正版を作成」で、発注が下書きへ戻り、4〜8章と同じ流れ（Draft編集 → 承認 → Demo Send → メーカー回答）を再度たどれることを示す。発注詳細画面の「発注内容の履歴（Revision）」「回答履歴（Revision別）」で、過去のRevision・回答が消えずに履歴として保持され続けていることを確認する。

## 19. G-SYSとの整合確認（Legacy PO Concurrency）

- 16章で正式PO番号を仮リンクしたOrderの発注詳細画面で、「G-SYS現在状態を基準として記録」を実行すると、その時点のG-SYS側の内容を基準として記録できることを示す。
- 記録後に再度確認すると「G-SYS側で発注内容の変更はありません」と表示されること、Legacy側のデータが変わっていた場合は「G-SYS側で発注内容が変更されています」という警告と、変更箇所の一覧（項目・記録時の値・現在の値・種別）が表示されることを示す。
- これは、Portal導入後もExcelの手作業運用が並行して残る場合に、G-SYS側で先に変更された内容とPortal側の認識のズレを検出するための仕組みであることを説明する。

## 20. History（発注履歴）とTimeline

- 「発注一覧」画面では、メーカー・ブランド・Statusでの絞り込みができ、各行にPO No.・Status・確認事項バッジ・更新日時が表示されることを示す。
- 発注詳細画面では、SKUごとに「推奨発注数 → 発注数量 → 回答数量」という3段階の値が並べて表示され、判断の過程が追跡できることを示す。
- 画面下部の「操作履歴」で、ドラフト作成から承認依頼・承認・Demo Send・メーカー回答確定・合意・修正版作成まで、すべての操作が実行時刻・実行者付きで時系列に記録されていることを示す。
- ダッシュボードのKPIタイル（発注候補／欠品／長期欠品／発注作成中／承認待ち／メーカー回答待ち／要確認／問い合わせ中）およびブランド別内訳表からも、対応する一覧画面へワンクリックで遷移できることを示す。ダッシュボードは分析画面ではなく、あくまで「今すぐ対応すべき件数」を示す操作起点（Action/Operation Cockpit）であることを明確に説明する。
- 発注候補一覧・SKU詳細には「在庫判定（暫定）」列／表示があり、欠品／長期欠品のどのSKUが該当するかを商品状態（通常／廃番／発注停止）とは別列・別バッジで確認できることを示す。この2つは独立した軸であり、たとえば商品状態＝「通常」のSKUが在庫判定＝「長期欠品」になっているケース（現在庫・発注残から見て長期欠品なだけで、商品自体は廃番・発注停止ではない）は矛盾ではないことを説明する。列見出し・バッジのTooltipに「暫定判定」である旨を明示しており、正式な判定条件は21章の質問どおりCustomer Review対象のままである。

## 21. 顧客へ確認する質問

デモの最後に、`docs/customer-review-decision-package.md`に集約済みの項目を、実際の画面を見せながら確認する。ここで聞くのは「その機能自体が必要か」ではなく、**「今回ご提案・実装している設計を、正式仕様として採用してよいか」**という採否確認である。新たな業務要件をこの場で追加提案することはしない。

**承認・権限について**
- 発注内容の承認は、ご提案どおり『担当者が作成→管理者が承認』という1発注ごとの2段階で問題ないか。
- 管理者が承認する際、その場で修正して承認してよいか。
- 一度承認された発注内容を後から直接編集できる必要があるか。
- 海外メーカー向けの発注について、担当者自身の判断で確定できるケースはあるか。
- 現行Prototypeは「メーカー回答の入力・保存・確定はOPERATOR、差異の受け入れ（合意）や修正版作成の判断はADMIN」という役割分担で実装している。この分担を正式仕様として採用してよいか。

**メーカーとの連絡について**
- Fromアドレスは担当者本人か、共通アドレス＋Reply-To方式か。
- 複数ADMIN時のCC対象は全員か、特定担当者か。
- Portalでの送信前編集可否・Template管理方法をどうするか。

**メーカー回答・差異について**
- 修正版（Revision）も初回と同じように管理者の承認が必要か。
- 双方合意（AGREED）の判定条件はどうあるべきか。
- 回答数量=0の場合の理由分類の正式リストはどうあるべきか。

**Statusについて**
- 欠品／長期欠品／廃番／発注停止の正式な業務定義。
- 供給状況（Supply Status）の正式な値・定義。

**G-SYS連携・Excel併存について**
- 正式PO番号の完全な採番規則、実際に誰が・いつ決定しているか。
- Portal導入後も手作業Excel Uploadを許可し続けるか。
- Portal/Excel競合時、どちらを正とするか。

**未納・再発注について**
- 未納問い合わせのTiming（納期超過閾値）とClose条件。
- 再発注ルール（新PO起票か元PO残継続か）。
