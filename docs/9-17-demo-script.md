# 9/17 デモ台本

このドキュメントは、Implementation Step 5の指示（20章相当）に基づき作成した、9/17お客様デモ用の台本である。

**前提**: このドキュメントは実装済みの挙動のみを記載しており、`勝手に新しい業務要件を追加しない`（Step 5指示）という制約に従う。顧客へ確認する質問はすべて要件MD 24章「9/17 顧客確認事項」に記載済みの項目から採っており、本書で新たに考案した項目は含まない。

**デモ前の準備**: `backend/demo-reset.sh` を実行し、Prototype PostgreSQLの業務データ（portal_order / portal_order_detail / supplier_response / supplier_response_detail / order_attention / audit_event）を空の状態にリセットしてから開始する（`portal_user`は保持されるため、ログインアカウントの再作成は不要）。Legacy Demo MySQLはこのリセットの対象外であり、常に同じ19 SKUのマスタ・PO実績データを保持している。

---

## 1. デモ開始時の説明

- 本システムは「G-SYS Online Ordering Prototype」であり、既存の基幹システム（Legacy G-SYS）に新たに追加するオンライン発注機能のプロトタイプであることを説明する。
- 画面上部の「デモ環境」バッジと、その下の警告バナー（Demo Environment - Legacy互換Demo Instanceのデータを表示しています）を指し、以下を明確にする。
  - 表示されているデータはLegacy本番データではなく、Legacy互換の使い捨てDemoインスタンスのデータであること。
  - 発注処理はすべて「Demo Send」というデモモードであり、実際にメーカーへメールが送信されることはないこと。
- 見せる一連の流れ（発注候補 → Draft → Preview → 発注確定 → メーカーへ送信 → メーカー回答 → 履歴）は、Recommended Qty計算を含め、既存Legacyの計算式（Formula）をそのまま利用していることを説明する。

## 2. Candidate List（発注候補一覧）で見るポイント

ダッシュボードの「発注候補」KPIタイルまたは「発注候補」ナビゲーションから発注候補一覧へ遷移する。

- 一覧には現在庫・安全在庫・発注残・当月販売数・リードタイム・推奨発注数・商品状態・単価が並んでいることを見せる。
- ブランド／メーカーのFilterで、ブランド別・メーカー別に発注候補を絞り込めることを示す。
- 商品状態Chip（通常／廃番／発注停止）が一覧上で一目でわかることを示す。
- SKUリンクをクリックするとSKU Detail画面（4章相当）へ遷移し、商品情報・在庫情報・発注情報・Legacy PO実績のみの履歴を確認できることを示す。

## 3. Recommended Qty（推奨発注数）の説明

- 推奨発注数は既存Legacyの発注判断Formula（4EU方式のDefault Formula、または一部SKUに設定されたItem別Formula）による計算結果であり、Prototype側で独自の計算式を新たに作っていないことを明確に説明する。
- Item別Formulaの例として `OD-TENT-001`（テント L型 グリーン）を示す。同SKUのみLegacy `MS_FORMULA` にItem別の計算式が設定されており、他の全SKUはLegacy Default Formulaで計算されていることを説明する。
- 推奨発注数が0件のSKU（例: `HM-TOWEL-001`、`KT-KNIFE-001`、`OD-CHAIR-001`）と、推奨発注数が算出されているSKU（例: `HM-MUG-001` 推奨5、`OD-TENT-001` 推奨3）を並べて見せ、「在庫が十分にある場合は0になる」という考え方を説明する。
- 発注残（Open PO）がある状態でどう推奨数に影響するかの例として `HM-RUG-002` / `OD-BAG-002`（いずれも発注残25）を示す。
- 当月販売数が多いSKUの例として `KT-PAN-001`（当月60）／`OD-BAG-002`（当月65）を示す。

## 4. Draftで人が判断する意味

- Candidate Listでは発注数量を直接編集しない（要件MD 26章 原則30）。チェックボックスでSKUを選び「ドラフト作成」した時点で、Order Qtyの初期値としてRecommended Qtyがそのままコピーされることを示す。
- Order Draft画面で発注数量を実際に人が変更できることを見せる（例: 推奨5 → 発注8のように変更）。
- 発注数量が推奨発注数から大きく乖離した場合（比率0.5未満または1.5超）に「要確認」警告Chipが表示されることを示し、機械的な推奨値をそのまま鵜呑みにせず、人が最終判断する仕組みであることを説明する。
- 「ドラフトを保存」でOrder Draftが保存され、以後同じDraftを何度でも編集・再保存できることを示す。

## 5. Preview（PO プレビュー）

- Order Draftから「PO プレビュー」で遷移し、SKU別の発注数量・単価・金額、合計SKU数・合計数量・合計金額を確認できることを示す。
- メーカー送付内容セクションで、宛先（To）・CC・件名・本文・添付ファイル名がプレビュー表示されることを示し、「デモモードのため、実際のメールは送信されません」という注記が明示されていることを確認する。
- Previewは原則READ ONLYであり、ここから直接内容を編集することはできず、編集は「発注内容を修正」でOrder Draftへ戻って行う設計であることを説明する。

## 6. Demo Send（発注内容確定・メーカーへ送信）

- 「発注内容を確定」ボタンで発注内容が確定し、Prototype PO No.（`PO-DEMO-YYYYMMDD-NNNN` 形式）が採番されることを示す。確定後はStatusが「発注準備完了」になる。
- 発注確定と実際の「メーカーへ送信」操作が分離されていることを説明する。「発注内容を修正」で確定前のDraftへ戻せる一方、送信後はDraftへ戻せないという段階的な設計になっている。
- 「メーカーへ送信」（Demo Send）を実行すると、Statusが「メーカー回答待ち」に変わり、メーカー回答画面へ自動的に遷移することを示す。この操作は1回の確認ダイアログを経て1回のみ実行される設計であり、二重送信は起きないことを説明する（History画面のTimelineで、Demo Send関連のイベントが1回しか記録されないことを見せると分かりやすい）。

## 7. Supplier Response（メーカー回答）

- メーカー回答画面で、SKUごとに回答数量・回答納期・回答理由メモを入力できることを示す。
- 「回答を保存」は何度でも実行でき、一部SKUのみ回答した状態でも保存できること（8章のPartial Responseと関連）を示す。
- 全SKUの回答数量が入力された状態でのみ「メーカー回答を確定」が実行可能になり、確定後はStatusが「メーカー確定済み」になり編集不可になることを示す。

## 8. 数量差異（回答数量が発注数量と異なる場合）

- 回答数量が発注数量と異なる値で保存されると、その行に「数量変更あり」のAttentionが表示されることを示す（例: 発注12に対し回答9など）。
- 回答数量が発注数量と一致する場合（例: 発注5に対し回答5）はAttentionが表示されないことも合わせて示し、差異がある場合のみ目印が付く仕組みであることを説明する。

## 9. 納期差異（回答納期が希望納期と異なる場合）

- 回答納期を入力すると、希望納期と異なる場合に「納期変更あり」のAttentionが表示されることを示す。
- 希望納期が未設定（—表示）の状態で回答納期を入力した場合も、値が異なる（未設定 → 具体的な日付）ため同様にAttentionが表示されることを示す。

## 10. 0回答（回答数量 = 0）

- 回答数量に0を入力して保存すると、「回答数量0 SKU数」の集計に反映され、未回答（空欄）とは明確に区別されて表示されることを示す。
- 未回答（空欄のまま）の状態では画面上「未回答」というプレースホルダーが表示され、0との違いが視覚的にも分かることを見せる。

## 11. Partial Response（一部SKUのみ回答）

- 複数SKUのDraftで、一部SKUのみ回答数量を入力して「回答を保存」すると、Status Chipの隣に「一部回答」というAttentionが表示されることを示す。
- 「回答済みSKU数: 1 / 2」のように未回答件数が可視化されることを示す。
- 残りのSKUも回答して再度保存すると、「一部回答」Attentionが自動的に解消される（ユーザーがAcknowledgeしなくても消える）ことを示し、History画面のTimelineで「確認事項の発生」→「確認事項の解消」という記録が残っていることを確認する。

## 12. Attention（確認事項）とAcknowledge

- 数量変更・納期変更のAttentionは、一部回答Attentionとは異なり自動解消されず、ユーザーが明示的に「確認済みにする」操作（Attention Chipの✓アイコン）をクリックするまでACTIVEのまま残ることを説明する。
- Order History Detail画面またはSupplier Response画面のどちらからでもAcknowledge操作ができることを示す。
- Acknowledge実行後、Attention Chipが画面上から消え、Historyの Timelineに「確認事項の解消」イベントが記録されること、さらにダッシュボードの「要確認」件数・ブランド別内訳が即座に減少することを示す（ダッシュボードへ戻って確認するとよい）。
- Attention行は物理削除されず、Acknowledge済みでも履歴としては保持され続けることを説明する（画面上は非表示になるが、データとしては消えていない）。

## 13. History（発注履歴）とTimeline

- 「発注履歴」一覧では、メーカー・ブランド・Statusでの絞り込みができ、各行にPO No.・Status・確認事項（Attentionバッジ）・更新日時が表示されることを示す。
- 発注詳細画面では、SKUごとに「推奨発注数 → 発注数量 → 回答数量」という3段階の値が並べて表示され、判断の過程が追跡できることを示す。
- 画面下部のAudit Timelineで、ドラフト作成から発注確定・Demo Send・メーカー回答確定まで、すべての操作が実行時刻・実行者付きで時系列に記録されていることを示す。
- ダッシュボードのKPIタイル（発注候補／欠品／長期欠品／発注作成中／メーカー回答待ち／要確認）およびブランド別内訳表からも、対応する一覧画面へワンクリックで遷移できることを示す。ダッシュボードは分析画面ではなく、あくまで「今すぐ対応すべき件数」を示す操作起点（Action/Operation Cockpit）であることを明確に説明する。

## 14. 顧客へ確認する質問

デモの最後に、要件MD 24章に記載済みの以下の項目を、実際の画面を見せながら確認する。新たな業務要件をこの場で追加提案することはしない。

**発注候補について**
- 現行Formula（Recommended Qty計算）をそのまま利用してよいか。
- 発注判断に必要な情報に不足はないか。
- 当月販売数（Recent Sales）の適切な期間。
- リードタイムの扱い。
- Recommended Qtyの考え方そのものについて。

**Workflowについて**
- Draft（下書き）Stepは業務上必要か。
- 発注内容の承認者は必要か。
- 誰がメーカーへ送信するか。
- Supplier Responseを誰が入力するか。
- 数量変更時に承認は必要か。
- 納期変更時に承認は必要か。

**Statusについて**
- 欠品／長期欠品／廃番／発注停止の正式な業務定義。

**Outputについて**
- 現行Excel POを維持するか。
- メーカー別のFormatが存在するか。
- メール送信までG-SYSで行うか。

**Integrationについて**
- Logizeroへいつ反映するか。
- 在庫更新のタイミング。
- 販売データ更新のタイミング。
- メーカー回答をどこまでシステム化するか。

**画面・運用詳細について**
- 発注時点からSKU別に希望納期を指定するケースの有無。
- Supplier Response Reasonの正式な区分。
- 回答数量 = 0の場合の業務Status／商品Statusの扱い。
- Supplier Responseの正式な完了条件（本Prototypeでは「全明細の回答数量が入力済み」を暫定条件としており、回答納期の入力は必須としていない）。
- Attentionを誰が確認・解消するか。
- 発注準備完了からDraftへ戻す正式な運用。
- 発注確定とメーカー送信の間に承認Workflowが必要か。
