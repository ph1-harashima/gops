# G-OPS Production Readiness Risk Register

**Status**: Planning document only — no Production system exists yet for any of these risks to materialize against. Written to inform the Gate sequence in `gops-production-readiness-checklist.md`, not as an incident log.

| # | Risk | Impact | Detection | Prevention | Recovery |
|---|---|---|---|---|---|
| 1 | Legacy DB accidental WRITE | Corrupts the customer's real production system of record — the single most severe possible outcome of this entire engagement | `LegacyReadOnlyIntegrationTest` regression; DB-level audit log on the real Legacy MySQL role (Ernest/DBA-side, not Portal's to configure) | 3-layer READ ONLY design (DB account SELECT-only, pool `readOnly=true` hardcoded, `@Transactional(readOnly=true)` everywhere) — already implemented and travels with the code unchanged into Production | Real Legacy DBA restores from their own backup/replication (entirely outside Portal's control or responsibility) |
| 2 | Wrong Supplier/Brand mapping (short code collision or mismatch) | Official PO numbered/routed to the wrong Supplier/Brand — wrong manufacturer receives an order | `official_po_short_code` Master has a uniqueness constraint per (code_type, business_code); ADMIN-entered, reviewable in the Master Maintenance UI before use | Values are Gulliver-decided and manually entered by ADMIN, never auto-generated by G-OPS (BR-08); require a second-person review step before Go-Live data entry (Operations process, not code) | Deactivate the wrong short code row (soft-delete, already supported); reissue with Reissue workflow (already implemented) |
| 3 | PO No. collision (two Orders assigned the same Official PO No.) | Legacy Import Batch would misattribute an order, or reject one silently, or (worst case) overwrite | `uq_portal_order_official_po_no` unique DB constraint (already exists — confirmed by this round's own accidental collision during heavy live testing, caught immediately as a DB-level constraint violation, never silently succeeded) | Same unique constraint + `OfficialPoNumberGenerator`'s per-(Supplier,Brand)-sequence concurrency control (already implemented, BR-08) | Constraint violation surfaces as an application error immediately — no silent corruption possible by design |
| 4 | Wrong PO recipient (Email sent to the wrong Manufacturer Contact) | Business-sensitive order information disclosed to the wrong party | Domain-mismatch warning already implemented in Mail Preview/Send (flags a To/CC address outside the registered Contact's own domain) | Contact resolution is priority-ordered and auditable; recipient override always requires explicit ADMIN action and is itself Audit-logged (`EMAIL_SENT` records the actual recipients used) | No unsend capability (inherent to email) — mitigated only by the pre-send Preview + domain-mismatch warning gate |
| 5 | Wrong Email Domain (typo'd or stale Contact address) | Same as #4 | Domain-mismatch warning (see #4) | Same | Same |
| 6 | Duplicate Send (Email sent twice for the same Order/Revision) | Manufacturer receives conflicting/duplicate instructions | `IdempotencyService`, key = `orderId-revisionNo`, DB UNIQUE-constraint-backed, load-tested under concurrent claims (8-thread test, 1 success guaranteed) | Same mechanism | Resend button is explicit ADMIN action post-failure only, never automatic |
| 7 | Duplicate Official PO Import (Excel placed into the Import Folder twice) | Legacy's Delete&Recreate import behavior on re-import could churn TR_PO unexpectedly if triggered twice for the same state | `IdempotencyService`, key = `orderId-officialPoNo-revisionNo` | Same mechanism, reused from the Email pattern | Retry-from-FAILED path re-places existing bytes (does not regenerate), avoiding a second distinct artifact |
| 8 | Import Folder unavailable (real Production transport, once built) | Official PO hand-off blocked entirely | Import placement failure maps to Integration Request's FAILED state (existing Attention-style pattern) | N/A yet — real transport (`ProductionImportFolderAdapter`) does not exist; this risk is currently **impossible to trigger** because the path cannot run at all (it throws before attempting anything) | Once real transport exists: retry-from-FAILED (already designed); until then, no Recovery is needed because no failure mode is reachable |
| 9 | SMTP unavailable (real Production endpoint, once connected) | Manufacturer email delivery blocked | Send failure caught, Order Detail shows Error + resend button, `EMAIL_SEND_FAILED` audited | N/A yet — `SmtpEmailSenderAdapter` is coded but unreachable (`@Profile("production")` + SafetyGuard); this risk is currently **impossible to trigger** | Once connected: resend button (already implemented) |
| 10 | Legacy batch (`PrOfficialPoImportBatch`) stopped/not running | Official PO placed in the Import Folder never gets picked up | `OfficialPoIntegrationService.confirmImport` (manual, on-demand) would report `NOT_YET_IMPORTED` indefinitely — this state is explicitly designed to be non-alarming on its own (it's the same state as "not yet processed"), so a genuinely stopped batch would look identical to normal latency | Entirely outside Portal's control — Legacy-side operational monitoring is Ernest's domain, not this codebase's | Ernest/Legacy-side restart of the batch process; no Portal action possible |
| 11 | Portal DB unavailable | Entire application down | `/actuator/health` reports DOWN (Portal DB only, not conflated with Legacy) | Backup/HA not yet designed (Audit §17) — currently a single Docker container, no redundancy of any kind | No Recovery mechanism exists yet — this is a genuine, currently-unaddressed Gap, not a mitigated risk |
| 12 | Secret leakage | Credential compromise, potentially including Legacy DB access | No Secret currently exists for Production (nothing to leak yet); Local/Demo secrets are openly committed by design (documented, accepted) | Select and implement a real Secret Manager before any Production credential is ever created (Checklist §Secrets) — until then, this risk is **latent, not yet live** | Standard credential-rotation procedure, to be defined once a real Secret exists |
| 13 | Network timeout (Legacy or Portal DB) | Requests hang or fail slowly under load | No explicit timeout configured today (HikariCP defaults only) — a real Gap | Add explicit connection/query timeout configuration (Checklist item, low-risk, implementable without any Customer/Ernest answer — an existing "Immediate Implementation Candidate" per `production-readiness-and-integration-boundary-audit.md` §19) | `LegacyUnavailableException`/`PORTAL_DB_ERROR` already map to graceful 503s rather than hangs, once a timeout is actually configured |
| 14 | Revision mismatch (wrong Revision's Excel/PDF/Email sent) | Manufacturer receives stale or incorrect order content | Explicit E2E regression exists for this exact scenario (`official-po-integration.spec.ts` Scenario M: "Manufacturer Send after Reissue targets the new ACTIVE Revision, not the SUPERSEDED one") | Revision state machine (ACTIVE/SUPERSEDED) enforced at the data-model level, not just UI | Reissue workflow already handles this; no additional Recovery needed |
| 15 | Demo/Test config in Production | A Production deployment accidentally runs with Demo DB URLs, Demo credentials, or `app.demo-features.enabled=true` | `SafetyGuardEnvironmentPostProcessor` — the entire class exists specifically to make this impossible, not just detected | Do not weaken the Allowlist beyond exactly what real Production hosts/DB names require (Checklist: SafetyGuard extension is a reviewed, one-way, minimal change) | N/A — by design, the application refuses to even start if this occurs |
| 16 | Wrong environment connection (Production code accidentally points at Legacy's real Production schema by name confusion, e.g. `goo`) | Same severity as #1 | `SafetyGuardEnvironmentPostProcessor`'s DB-name Allowlist explicitly excludes `goo` (the real Legacy schema name) by name, called out in the class's own Javadoc as a deliberate, explicit exclusion | Same — Allowlist review before any extension (Checklist) | N/A — blocked at startup |

## Risk Summary by Current State

- **Already mitigated by existing, working code** (#1, 2, 3, 4, 5, 6, 7, 14, 15, 16): no further Production-specific action needed beyond what Gate 2-4 already require (real Secret/DB provisioning) — the *safety mechanism* itself does not need to change.
- **Currently impossible to trigger, because the feature doesn't reach Production yet** (#8, 9): will need re-evaluation once `ProductionImportFolderAdapter`/`SmtpEmailSenderAdapter` are actually connected (Gate 5/6) — not a Gap today, but do not mistake "impossible today" for "solved."
- **Genuine, currently-unaddressed Gaps** (#10 partially, #11, #12, #13): Backup/HA (#11), Secret Management (#12), and explicit timeouts (#13) have no mechanism at all yet. These map directly to Checklist items and should not wait for Ernest/Gulliver answers — #13 in particular is implementable today with zero external dependency.
